# 文档同步与维护指南

文档应与同一提交中的实现保持一致。本文定义此后维护 SimpleGit 时的文档责任、更新流程和检查清单。

同步基准：`SimpleGit 0.1.0`，核对日期 `2026-11-15`。

## 基本原则

- 同一改动同时包含代码、测试和受影响文档。
- 当前实现以源码和配置为准；旧设计或计划不能覆盖已验证的当前行为。
- 一处只维护完整事实，其他文档用链接连接，减少副本漂移。
- 命令、版本、路径和测试数字必须来自实际执行环境。
- 日期化验证记录代表快照，不自动代表当前版本；重新验证后更新基准或新增记录。

## 文档责任矩阵

| 改动类型 | 必须检查的文档 |
| --- | --- |
| 产品范围、用户操作、环境要求 | 根目录 `README.md` |
| 模块职责、数据流、安全不变量 | `docs/architecture.md` |
| Tauri 命令、参数、返回或错误码 | `docs/api.md`、`src/types.ts` 对应说明 |
| 开发命令、测试分层、扩展步骤 | `docs/development.md` |
| 文档结构、同步规则、审查流程 | 本文档和 `docs/README.md` |
| 实际构建、安装包、真实环境烟测 | `docs/manual-test.md` |
| 首版设计边界或默认提交规则 | `docs/superpowers/specs/2026-11-15-simplegit-design.md` |

实施计划是历史过程记录，通常不回写成当前状态；只有其任务说明会误导后续开发时，才补充“历史记录”说明或迁移有效信息。

## 单次改动流程

1. 用代码、配置和测试确认当前行为，不先假设文档正确。
2. 找出面向用户、开发者和架构维护者的受影响文档。
3. 修改实现和测试；同时更新权威文档。
4. 搜索旧名称、旧参数、旧路径和旧命令，删除已失效引用。
5. 检查 Markdown 相对链接指向实际文件。
6. 执行与改动影响匹配的验证命令。
7. 审查 diff，确认文档没有描述尚未实现或未验证的能力。

## 常见同步触发点

### 命令协议变化

需要同步：

- `src-tauri/src/commands.rs`
- `src-tauri/src/lib.rs`
- `src/types.ts`
- `src/api.ts`
- `src/api.test.ts`
- `docs/api.md`
- 必要时 `docs/architecture.md`

只改 Rust 命令而不更新前端，或只改前端参数而不更新 Rust，都属于不完整改动。

### 用户行为变化

需要同步：

- 对应组件与 `App.tsx`
- 前端交互测试
- 根目录 `README.md`
- 若影响系统边界或安全属性，再更新 `docs/architecture.md`

“自动刷新”“默认选择”“取消后保留什么”“何时禁用按钮”等行为均属于用户可观察契约。

### 配置结构变化

需要同步：

- `settings/mod.rs` 和 `settings/store.rs`
- 设置与迁移测试
- `docs/architecture.md` 的持久化章节
- 根目录 `README.md` 中用户可见的存储与应用设置说明

新增字段必须说明旧设置文件如何加载。不得把密钥字段加入普通 JSON。

### 依赖、工具链或打包变化

需要同步：

- `package.json` / `package-lock.json`
- `src-tauri/Cargo.toml` / `Cargo.lock`
- Tauri 配置和 capabilities
- 根目录 `README.md`
- `docs/development.md`
- 重新执行并记录打包验证

不要只更新版本号而保留旧命令或旧安装包路径。

## 文档编写约定

- 默认使用简体中文；代码标识符、命令、错误码和配置键保持原样。
- 先写结论和适用条件，再补充实现细节。
- 表格用于稳定映射，不使用大段重复叙述。
- 示例命令可在当前平台直接执行，并使用项目实际脚本或 Cargo manifest 路径。
- 不写无法核验的“应该可以”；未验证状态要明确标注。
- 不在文档中记录 API Key、令牌、用户凭据或敏感技术详情。
- 引用源码时优先写仓库相对路径；讨论某次具体行为时可使用行号，但不要批量复制会快速过期的行号。

## 验证清单

每次准备提交前：

- [ ] 根目录 `README.md` 的功能、环境、命令和安装包信息仍准确。
- [ ] `docs/README.md` 的导航包含所有维护文档。
- [ ] `docs/api.md` 命令数量、名称、参数、返回和错误码与源码一致。
- [ ] `docs/architecture.md` 的模块职责、数据流和安全不变量与实现一致。
- [ ] `docs/development.md` 的脚本和目标文件实际存在。
- [ ] 工作区路径、设置路径、服务名和构建目标没有改变而未说明。
- [ ] 相对 Markdown 链接没有失效。
- [ ] 验证记录明确区分“已通过”“未执行”“尚未验证”。
- [ ] `git diff --check` 无空白错误，最终 diff 无构建产物或密钥。

## 文档审查问题

审查时优先问：

1. 新维护者能否从 `docs/README.md` 找到正确资料？
2. 文档是否混淆“设计意图”“历史计划”和“当前行为”？
3. 同一事实是否在多个文件重复且可能漂移？
4. 新增能力是否在用户操作、架构和测试三个层面都有关联说明？
5. 文档中的命令是否实际可执行，结果是否来自当前环境？
6. 是否把尚未验证的平台或服务写成已支持？

## 当前已知验证缺口

以下内容不能写成已发布级完成：

- macOS 实机启动、Keychain 和打包。
- 真实云端模型服务的在线计费流程。
- 真实带认证 remote 的 Push/Pull。
- MSI 安装后的升级、卸载和代码签名。

这些缺口记录在 `docs/manual-test.md`。补齐验证后，同时更新该记录、根目录 `README.md` 和 `docs/development.md` 的平台说明。
